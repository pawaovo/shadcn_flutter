## The failed network-service child is identifiable

`/proc` command-line evidence identifies PID 2805 as
`--utility-sub-type=network.mojom.NetworkService`, with executable
`/opt/microsoft/msedge/msedge` and start ticks 24511. It is first sampled at
+17.804 s (JSONL line 59), then appears as S/`futex_do_wait` for 15 samples. Its
own log says it terminates after 15 seconds without a connection at
`06:20:33.357817`, +32.298817 s after `InitSession` starts
(`framework/msedgedriver.log`, line 103). It is then sampled as Z on lines
74–80, +32.965 s through +39.032 s. Its sampled CPU-time delta is zero ticks and
main-thread runtime delta is 608656 ns. It is not itself sampled waiting in D.

The browser reports the network service crash/restart at `06:20:41.046404`,
+39.987404 s (`framework/msedgedriver.log`, line 137). A replacement network
service PID 3010, start ticks 26788, appears in JSONL line 81 at +40.045 s and
remains observed. The browser still has a `folio_wait_bit_common` observation
in that sample. Renderer PID 2846 first appears at +38.021 s and is D in all
seven startup samples: one `do_mprotect_pkey`, followed by six folio waits.

This sequence establishes a failed child connection during the resource-heavy
startup, its zombie interval, and subsequent replacement. It does not establish
which thread or dependency prevented the initial connection, nor prove that the
child failure caused the later persistent navigation wait.

## The later passing suite is informative but is not a fresh-runner control

Both session identities report actual Microsoft Edge and EdgeDriver
`152.0.4191.53`, `pageLoadStrategy: normal`, and `pageLoad: 300000`. The later
browser suite starts session creation at `1788503187.169` and returns at
`1788503188.063` (`browser/msedgedriver.log`, lines 7 and 281). Its initial
position and size requests pass; the W3C suite subsequently passes.

PID 3450 has 58 total observations: R 1 / S 56 / D 1. Its single D/folio wait is
at +11.199 s, after successful startup, during the later journey. The startup
has only one sample (JSONL line 39). Its surrounding bracket, lines 38–40,
spans -0.988050 s to +1.040906 s and has host I/O `some` +0.323884 s / `full`
+0.224228 s; that 2.029-second bracket is not an exact 0.894-second measurement.
Network service PID 3488 remains observed without the failed suite's recorded
termination/restart sequence.

The comparison shares one job and a browser version, but the second session
starts after the first failure and may benefit from filesystem cache residency
or other changed host state. It does not isolate the cause.

## What these captures cannot answer

- The old observer did not save `minflt`, `majflt`, or `/proc/PID/io`. Fault counts
  and bytes read cannot be recovered from these JSONL files.
- `folio_wait_bit_common` does not identify a file. It cannot distinguish browser
  executable pages from shared libraries, snapshots, or other file-backed data.
- State and wait channel are main-thread point samples, not continuous traces.
  D-sample counts are not elapsed seconds. CPU ticks remain ticks because the
  sidecars did not record their frequency; `schedstat` supplies explicit ns.
- Host PSI and visible root-cgroup counters are not browser-specific accounting.
  Missing root memory-controller files are recorded as unavailable, not zero.
- These per-suite artifacts do not contain post-run executable hashes or runner
  `ImageVersion`. The next comparison must record both before interpreting it.

The next manual pair tests one concrete prediction: if prereading the actual
browser ELF materially affects this startup path, it should change the early
fault/I/O/wait evidence and possibly the child connection outcome. If the early
wait disappears while the original position command still fails, the later
navigation/driver state remains a separate target for investigation. A passing
pair without reproduction does not identify a repair or establish a failure rate.
